# Каталог проектов: make-цели, shell-скрипты и compose каждого проекта

## Зачем

На продакшене всё живёт в `/opt`: тридцать пять независимых проектов, у каждого свой `docker-compose.yml`, у многих `makefile`, рядом лежат shell-скрипты. Плюс скрипты самого `/opt` — `up-all.sh`, `clear-docker.sh`, `check-vk-token-scopes.sh`.

```
/opt
├── up-all.sh                 clear-docker.sh    check-vk-token-scopes.sh
├── crm-boss/
│   ├── docker-compose.yml    makefile
│   └── check.sh  checkmig.sh  probe-search-date.sh
├── tg-boss-crm/  multichat-bot/  content-factory/  … всего 35
```

Сейчас раннер исходит из **одного** корня проекта: `findProjectRoot` поднимается вверх и на этом останавливается. В `/opt` такая модель бесполезна — нужен вид на все проекты сразу, с их целями make, скриптами и контейнерами.

## Границы

Входит: секция `Проекты` со списком дочерних проектов и самого корня, плоский список запускаемого для выбранного проекта (контейнеры, цели make, shell-скрипты, npm-скрипты), запуск задачей и запуск в терминале, подтверждение перед каждым запуском, отдельный `ComposeStore` на проект с ленивым созданием.

Не входит: рекурсивный обход глубже одного уровня, редактирование makefile или скриптов, передача аргументов целям и скриптам, разбор `.env` проектов, параллельный опрос контейнеров всех проектов, запуск на удалённом хосте.

**Топология.** Раннер запускается по ssh на самом продакшен-хосте, в `/opt`. Docker и файлы локальные.

## Экран

Левая колонка получает секцию `📦 Проекты`: первая строка — сам корень, дальше дочерние проекты по алфавиту. Курсор на проекте — справа его запускаемое.

```
┌ Задачи ───────────────────┬ crm-boss • /opt/crm-boss • без фильтра • 8 ───────┐
│ ▶ Команды                 │ ▸    контейнеры 12/14                            │
│ 📦 Проекты (35)           │ make up                                          │
│   /opt (корень)           │ make down                                        │
│   crm-boss                │ make logs                                        │
│   content-factory         │ sh   check.sh                                    │
│   multichat-bot           │ sh   checkmig.sh                                 │
│ ● Запущено (1)            │ sh   probe-search-date.sh                        │
│   ● sh up-all.sh   0:12   │ npm  build                                       │
└───────────────────────────┴──────────────────────────────────────────────────┘
 печатай фильтр  ↑↓ выбор  Enter действия  Tab/←/Esc назад
```

Список плоский, но отсортирован по типу: контейнеры, make, скрипты, npm. Буквы фильтруют по всему сразу — набрал `che`, остались `check.sh` и `checkmig.sh`. При тридцати пяти проектах главная операция — быстро найти нужное, а не изучать структуру, поэтому фильтр важнее группировки по подменю.

Строка `▸ контейнеры 12/14` уводит в существующий список контейнеров этого проекта, `Esc` возвращает к списку запускаемого — тот же приём, что трасса джобы над списком джоб.

`Enter` на любой запускаемой строке — make, скрипт или npm — открывает меню из двух пунктов:

```
┌ check.sh ────────────────────────────────────┐
│ ▸ Запустить (задачей, с логом)               │
│   Запустить в терминале                      │
└──────────────────────────────────────────────┘
```

**Почему два пункта, а не один.** Задачи запускаются со `stdin: ignore` — правильно для сборок, но интерактивный скрипт (`Continue? [y/N]`) зависнет молча, и ответить будет нечем. «Запустить в терминале» сворачивает TUI, отдаёт скрипту настоящий терминал и возвращает TUI по завершении — это единственный работающий путь для всего, что спрашивает.

Дальше — подтверждение с точной командой и рабочей папкой:

```
┌ Запустить check.sh ──────────────────────────┐
│ bash /opt/crm-boss/check.sh                  │
│ рабочая папка: /opt/crm-boss                 │
│                                              │
│ y — да    n — отмена                         │
└──────────────────────────────────────────────┘
```

Спрашивается **всегда**, без списка «безопасных» имён: отличить `check.sh` от `clear-docker.sh` по имени нельзя, а второй на проде звучит недвусмысленно.

## Клавиши

| Клавиша | Где | Что делает |
|---|---|---|
| буквы | список запускаемого | фильтр |
| `↑` `↓` | список запускаемого | выбор строки |
| `Enter` | make, скрипт или npm-строка | меню: запустить / запустить в терминале |
| `Enter` | строка контейнеров | список контейнеров проекта |
| `Esc`, `←` | список контейнеров | назад к запускаемому |
| `r` | строка проекта | пересканировать проект и перечитать `ps` |

## Объектная модель

**`ProjectIndex`**
- Конструктор `({ root, fsImpl = fs })`, метод `refresh()`, `projects()` → `Project[]`, `get(dir)`.
- Сканирует `root` на **один уровень вниз** плюс сам `root`. Один уровень — сознательно: рекурсия по `/opt` уперлась бы в тома docker, логи и `node_modules`, а вложенные монорепо покрывает существующий `WorkspaceIndex`.
- Проект — папка, где есть хоть что-то из: compose-файл (`docker-compose.yml`, `compose.yaml`, `docker-compose.yaml`), makefile (`makefile`, `Makefile`, `GNUmakefile`), `*.sh`, `package.json` с непустым `scripts`.
- `Project` = `{ name, dir, composeFile: string|null, makefile: string|null, scripts: string[], hasPackageJson: boolean }`.
- `node_modules`, `.git` и скрытые папки в список не попадают. Папка без прав на чтение пропускается.

**`MakefileTargets.parse(text)`** → `string[]`
- Цели: строки вида `^[A-Za-z0-9_.-]+\s*:` (с зависимостями или без).
- Отсеиваются: шаблонные правила с `%`, служебные цели с точки (`.PHONY`, `.SILENT`), присваивания (`VAR := x`, `VAR = x`, `VAR ?= x`, `VAR += x`), комментарии, строки с отступом (тело правила), двойные двоеточия оставляем как цель.
- Чистая функция над строкой: тестируется без файловой системы. `make -qp` не вызывается — он разбирает всё окружение и на кривом makefile способен наделать лишнего.

**`MakeCommand`** — спека задачи: `make -C <dir> <target>`; `label()` → `make <target> (<имя проекта>)`.

**`ShellCommand`** — спека задачи: `bash <абсолютный путь скрипта>`, `cwd` = папка проекта; `label()` → `sh <имя файла> (<имя проекта>)`.

`bash`, а не запуск файла напрямую: у скриптов может не быть бита `+x`, а `sh` не понимает bash-измов, которые в таких скриптах обычно есть.

**`projectRunnables(project, { composeStore })`** → строки правой колонки:
- `{ kind: 'containers', label: '▸ контейнеры <up>/<total>' }` — если есть compose-файл;
- `{ kind: 'make', target, label: 'make <target>' }` — по цели;
- `{ kind: 'sh', script, label: 'sh <файл>' }` — по скрипту;
- `{ kind: 'npm', command, label: 'npm <команда>' }` — если есть `package.json` со скриптами.

**Изменение существующего кода.** `ComposeStore` сейчас один на приложение — станет по одному на проект, в `Map` с ленивым созданием: захожу на проект, тогда экземпляр и создаётся, тогда и опрашивается. Опрос остаётся только для проекта под курсором. Тридцать пять одновременных `docker compose ps` на проде не случится ни при каком раскладе.

Секция `Проекты` появляется, только если в текущей папке нашлись дочерние проекты. Запустил внутри одного проекта — всё как сейчас, лишней секции нет.

**Отдельная секция `🐳 Compose` и секция `Проекты` вместе не показываются.** Когда есть дочерние проекты, корень уже присутствует первой строкой в `Проекты`, и его контейнеры доступны оттуда; вторая секция про тот же compose дублировала бы одно и то же двумя путями с раздельным состоянием. Внутри одиночного проекта секция `Compose` остаётся как сейчас.

Запуск npm-строки идёт через то же меню и то же подтверждение, что make и скрипты. Это расходится с секцией `Команды`, где Enter по сервису запускает сразу, и расхождение осознанное: в `Команды` ты выбираешь скрипт своего монорепо на своей машине, а здесь стоишь в `/opt` на проде, где `npm run deploy` чужого проекта — то же самое по последствиям, что `clear-docker.sh`.

Состояние правой колонки помнится по проекту, как уже помнится по команде, задаче и пайплайну: вернулся на `crm-boss` — тот же фильтр и та же выбранная строка.

## Потоки

**Выбрать проект.** Курсор на строке проекта → справа список запускаемого. Если у проекта есть compose, его `ComposeStore` создаётся при первом заходе и опрашивается раз в 5 секунд, пока курсор здесь.

**Запустить скрипт или цель.** `Enter` → меню (задачей / в терминале) → подтверждение с командой и папкой → задача с логом либо свёрнутый TUI. Ненулевой код виден в статусе задачи; лог остаётся после завершения.

**Контейнеры проекта.** `Enter` на строке контейнеров → существующий список с фильтром и меню действий (логи, обновить, образы и откат, рестарт, стоп). `Esc` — назад к запускаемому.

**Обновить список.** `r` на строке проекта пересканирует его файлы (появился новый скрипт — появится строка) и перечитает `ps`.

## Отказы

- **Папка без прав на чтение** — пропускается. Если из-за этого не нашлось ни одного проекта, секция объясняет причину, а не молчит.
- **`make` не установлен** — задача падает, текст ошибки первой строкой лога, TUI продолжает работать.
- **Makefile без целей** — строк make просто нет.
- **Пробелы и кавычки в именах** — argv массивом, shell не используется, экранировать нечего.
- **Интерактивный скрипт, запущенный задачей** — зависнет на чтении stdin; `s` снимает его вместе с деревом процессов. Для такого есть «Запустить в терминале», и в подсказке меню это написано.
- **Проект без compose** — строки контейнеров нет.
- **Пустая папка среди проектов** — в список не попадает.

## Проверка

Юнит-тесты на временных деревьях и инжектированном `spawn`, ни один не зовёт настоящие `make`, `bash` или docker:

- `ProjectIndex`: находит дочерние проекты каждого сорта (compose, makefile, скрипты, package.json) и сам корень; пропускает пустые папки, `node_modules`, `.git`, скрытые; переживает папку без прав; сортирует по имени.
- `MakefileTargets.parse`: цели с зависимостями и без, `%`-шаблоны, `.PHONY`, присваивания всех видов, комментарии, тело правила с отступом, двойное двоеточие.
- `MakeCommand`, `ShellCommand`: точный argv, `cwd`, подпись.
- `projectRunnables`: порядок типов, наличие строки контейнеров только при compose-файле, счётчик из `ComposeStore`.
- Карта `ComposeStore`: создаётся лениво, повторный заход отдаёт тот же экземпляр, опрашивается только выбранный проект.

Дымовой прогон UI на заглушке blessed: секция `Проекты` появляется при дочерних проектах и отсутствует внутри одиночного; фильтр находит `check.sh` набором трёх букв; `Enter` по скрипту открывает меню, а не запускает; подтверждение показывает команду и папку; отказ не запускает ничего; согласие создаёт задачу; «в терминале» сворачивает и восстанавливает screen; строка контейнеров уводит в список контейнеров, `Esc` возвращает.
