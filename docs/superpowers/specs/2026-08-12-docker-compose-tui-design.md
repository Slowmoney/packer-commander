# Docker Compose в TUI: обновление, логи, откат по digest

## Зачем

Ежедневные команды на проде набираются руками:

```bash
docker compose pull && docker compose up -d
docker compose pull backend && docker compose up -d backend
```

Логи приходится смотреть отдельным `docker compose logs -f`, переключаясь между окнами. А когда залитый образ оказывается сломанным, откат делается вручную: найти предыдущий digest, открыть compose-файл, заменить тег на `image: repo@sha256:...`, поднять сервис.

Откат особенно болезненный из-за того, что в проекте **изменяемые теги**: все 45 сервисов ссылаются на `registry.gitlab.com/ssmm_ai/vk-boss-core/vk-boss-core:<имя-сервиса>`. После нового пуша тег указывает на другой образ, и чем был предыдущий — нигде не записано.

## Границы

Входит: секция compose в левой колонке, список контейнеров со состоянием, живые логи как обычная задача, `pull && up -d` для сервиса и для всего проекта, рестарт, стоп, откат на любой образ из локального кеша или реестра GitLab.

Не входит: журнал развёртываний (см. «Почему не журнал»), постоянное закрепление digest в compose-файле, `exec sh` в контейнер, управление удалённым docker через контексты или `DOCKER_HOST`, сборка образов, `docker compose config`, диффы env.

**Топология.** Раннер запускается по ssh на самом продакшен-хосте, docker локальный. Контексты и удалённое исполнение из объёма исключены сознательно: они добавляют режим, в котором легко перепутать окружение, а сценарий пользователя их не требует.

## Почему не журнал развёртываний

Первым решением просится журнал: запоминать при каждом `pull`, какой digest был запущен, и откатываться по нему. Он не годится: журнал пуст именно в тот момент, когда впервые нужен — при первом же инциденте после установки раннера, — и живёт только там, где его успели накопить.

Источники правды берутся из системы, а не из накопленной истории:

- `docker images --digests <repo>` — что уже скачано локально, с digest и датами. Предыдущий образ лежит там, пока его не выпрунили.
- **GitLab Registry API** — что вообще можно скачать. Хост, путь проекта и токен уже есть в `GitLabClient`, добавляется только scope `read_registry`.
- `docker inspect <container>` — что запущено прямо сейчас.

Это работает с первого запуска и не требует, чтобы раннер что-то «застал».

## Экран

Левая колонка получает секцию с одной строкой на compose-проект. Курсор на ней — справа контейнеры проекта.

```
┌ Задачи ────────────────────┬ vkboss-light • 43/45 up • фильтр: gpt ───────────┐
│ ▶ Команды                  │ ▸ весь проект (45)                               │
│   build                    │ ● gptboss-llm        up 3d      2.1 ГБ           │
│   serve                    │ ● gptboss-chat       up 3d      1.4 ГБ           │
│ 🐳 Compose                 │ ✗ gptboss-history    exited(1)  2 мин назад      │
│   vkboss-light  43/45      │ ⇤ gptboss-nac        up 5m  локально переопределён│
│ ● Запущено (1)             │                                                  │
│   ● logs gptboss-llm 0:42  │                                                  │
│ ✓ Завершено (2)            │                                                  │
└────────────────────────────┴──────────────────────────────────────────────────┘
 Запущено: 1  Готово: 2  Ошибок: 0 │ печатай фильтр  ↑↓ контейнер  Enter действия
```

Навигация повторяет то, что уже есть: команда → её сервисы, пайплайн → его джобы, compose → его контейнеры. Новых понятий в интерфейсе не появляется.

Буквы фильтруют список контейнеров — при 45 сервисах это обязательно, а не удобство. Состояние правой колонки (фильтр, выбранный контейнер, прокрутка) помнится для строки compose так же, как для остальных пунктов.

Первая строка списка — `▸ весь проект (N)`: через неё делаются операции над всем compose сразу, тем же способом, что над отдельным контейнером. Отдельных «глобальных» клавиш не появляется.

**Действия — через меню, а не через буквы.** `Enter` на контейнере открывает список действий:

```
┌ gptboss-llm ─────────────────────────────────┐
│ ▸ Логи                                       │
│   Обновить (pull + up -d)                    │
│   Образы и откат                             │
│   Рестарт                                    │
│   Стоп                                       │
└──────────────────────────────────────────────┘
 ↑↓ выбор  Enter выполнить  Backspace назад
```

Так сделано по двум причинам, и обе весомые. Первая: в правой колонке буквы заняты фильтром — навесить `u` на «обновить» значило бы, что при наборе фильтра `update-worker` половина букв уходит в деплой. Ровно на этом раннер уже спотыкался, когда `w` означало watch-режим. Вторая: случайная буква на проде стоит развёртывания, а случайный `Enter` открывает безобидное меню. Действия при этом остаются в два нажатия и не требуют помнить хоткеи.

**Логи — обычная задача.** Пункт «Логи» запускает `docker compose logs -f --tail=200 <svc>`; задача появляется в «Запущено» с подписью `logs <svc>`, и дальше это тот же лог, что у npm-задач: поиск `/`, копирование `y`, режим на весь экран `z`, `s` чтобы прекратить слежение. Стрим стартует только по выбору пункта — ходьба курсором по 45 контейнерам ничего не запускает.

Каталог образов (пункт «Образы и откат») — список поверх, локальные и реестровые вместе:

```
┌ Образы gptboss-llm ──────────────────────────────────────────────────┐
│ Фильтр: (пусто)                                                      │
│                                                                      │
│ ● sha256:1f3a9c…  локально  12.08 21:04   ← запущен сейчас           │
│   sha256:9bd2e1…  локально  11.08 18:22                              │
│   sha256:77aa04…  реестр    10.08 09:15                              │
│   sha256:4c1102…  реестр    08.08 14:40                              │
└──────────────────────────────────────────────────────────────────────┘
 ↑↓ выбор  Enter откатить  Backspace назад
```

## Клавиши

| Клавиша | Где | Что делает |
|---|---|---|
| буквы | список контейнеров | фильтр |
| `↑` `↓` | список контейнеров | выбор контейнера |
| `Enter` | контейнер или `весь проект` | меню действий |
| `Enter` | пункт меню | выполнить (записи — через подтверждение) |
| `Backspace`, `Esc` | меню, каталог образов | назад |
| `r` | строка compose | перечитать `ps` немедленно |

Пункты меню для контейнера: «Логи», «Обновить (pull + up -d)», «Образы и откат», «Рестарт», «Стоп». Для строки `весь проект`: «Обновить всё (pull + up -d)» и «Логи всего проекта».

## Объектная модель

Ядро прирастает четырьмя классами. Ни один не знает про blessed, все внешние вызовы инжектируются.

**`ComposeProject`**
- `find(startDir)` — поднимается от папки, ищет `docker-compose.yml`, `compose.yaml`, `docker-compose.yaml` (в этом порядке), останавливается на `.git` тем же приёмом, что `findProjectRoot`.
- Читает `name:` из файла; нет поля — берёт имя папки.
- Поля: `file` (абсолютный путь), `name`. Больше ничего: состояние — не его дело.

**`DockerCli`**
- Конструктор `({ composeFile, dockerPath = 'docker' })`.
- Строит только argv, массивами, без shell: `ps()`, `logs(service, { tail = 200 })`, `pull(service)`, `pullAll()`, `up(service, { noDeps = false })`, `upAll()`, `restart(service)`, `stop(service)`, `images(repo)`, `inspect(container)`, `pullDigest(repoWithDigest)`, `tag(source, target)`.
- Каждый метод отдаёт `{ command, args, shell: false }` — тот же вид, что `NpmCommand.spawnTarget()`, поэтому задачи умеют исполнять и то, и это.
- Отсутствие shell — не стилистика: аргументы приходят из compose-файла и из реестра, и склейка строкой открыла бы дорогу к подстановке.

**`ComposeStore extends EventEmitter`**
- Устроен как `PipelineStore`: `items`, `status` (`idle | loading | ready | error | disabled`), `reason`, событие `changed`.
- `refresh()` — `ps --format json`, парсинг через `parsePsOutput`.
- `pinned` — множество сервисов, у которых локальный тег переопределён откатом.
- `hasRunning()`, `counters()` → `{ up, total }` для подписи в левой колонке.
- Только чтение. Опрос раз в 5 секунд, пока курсор на compose или пока жива docker-задача; ничего не пишет по таймеру.

**`parsePsOutput(text)`**
- `docker compose ps --format json` отдаёт JSON **построчно**, по объекту на строку, а не массивом; в части версий — всё-таки массивом.
- Поля в разных версиях различаются регистром (`Name`/`name`, `State`/`state`, `Service`/`service`).
- Парсер принимает оба формата, приводит регистр, пропускает битые строки и возвращает `{ service, name, state, status, image, exitCode }[]`.

**`ImageCatalog`**
- `build({ local, registry, current })` → единый список `{ digest, tags, sources: ('local'|'registry')[], createdAt, isCurrent }`.
- Дедуп по digest, сортировка по `createdAt` вниз, текущий помечается.
- Локальные образы означают «откат мгновенный, качать нечего» — в списке это видно.

**`GitLabClient`** дополняется `registryRepositories()` и `registryTags(repositoryId)`; digest и дата берутся из деталей тега. Токен требует `read_registry` вдобавок к `read_api`.

## Правка существующего кода

Две штуки, без которых новое встанет копипастой.

**Общая спека команды.** Сейчас `Task` жёстко держит `NpmCommand`, а `TaskManager.start()` его создаёт. Вводится общий вид: у спеки есть `args()`, `spawnTarget()`, `label()`; `NpmCommand` — одна реализация, `DockerCommand` — вторая. `Task`, `TaskManager`, логи, поиск, стоп с убийством дерева процессов и хранение состояний по пунктам не меняются.

**Цепочки команд.** `u` и откат — не одна команда: `pull` → `up -d`, и `pull digest` → `tag` → `up -d --no-deps`. Добавляется `TaskManager.startSequence({ label, targets })`: одна задача, один лог, шаги идут по очереди, ненулевой код прерывает остаток и оставляет задачу в `failed`. Так в одном логе видно, на каком шаге всё встало, и `&&` через shell не нужен.

## Потоки

**Обновить сервис** (меню → «Обновить»). `ConfirmView` с точными командами → `startSequence` из `pull <svc>` и `up -d <svc>` → задача в «Запущено», вывод течёт в лог → по завершении `ComposeStore.refresh()`, пометка `pinned` для этого сервиса снимается.

**Обновить всё** (строка `весь проект` → «Обновить всё»). То же, но `pull` и `up -d` без аргумента; в подтверждении — число сервисов из `ps`.

**Логи** (меню → «Логи»). `logs -f --tail=200 <svc>` как задача. Остановка — `s` на самой задаче: она убивает дерево процессов, как любая другая.

**Откат** (меню → «Образы и откат» → выбор). Каталог собирается из трёх источников параллельно; отсутствие реестра не мешает. Выбор → `ConfirmView` с digest, датой образа и предупреждением про расхождение с реестром → `startSequence`: `pull repo@sha256:…` (пропускается, если образ уже локальный), `tag <digest> repo:<тег>`, `up -d --no-deps <svc>` → сервис помечается `pinned`.

**Почему ретег, а не правка файла.** Compose ссылается на изменяемый тег, поэтому локальный ретег меняет то, что поднимется, не трогая файл под git. Это аварийный откат за секунды — ровно тот сценарий, ради которого фича существует. Цена честно показывается: пометка `⇤ локально переопределён` держится до следующего `pull` этого сервиса, а следующий `u` осознанно уедет вперёд на свежий образ. Постоянное закрепление digest в compose-файле — отдельная задача, не в этой.

## Отказы

- **`docker` не найден или демон не отвечает** — секция показывает причину, остальной раннер работает как раньше; ровно как секция GitLab без токена.
- **Compose-файл не найден** — секции нет вообще.
- **Реестр недоступен или у токена нет `read_registry`** — каталог показывает только локальные образы и объясняет, почему нет реестровых. Откат на скачанный образ работает без сети.
- **Пустой список контейнеров** — нормальное состояние «ничего не поднято», не ошибка.
- **Шаг цепочки упал** — остаток не выполняется, задача `failed`, вывод обоих шагов в одном логе.
- **`ps` вернул мусор в одной строке** — строка пропускается, остальные показываются.

## Проверка

Юнит-тесты на инжектированном `spawn`, ни один не зовёт настоящий docker:

- `DockerCli` строит ожидаемые argv для всех команд, включая `--no-deps`, `--tail`, `-f <composeFile>`.
- `ComposeProject.find` находит файл вверх по дереву, соблюдает порядок имён, читает `name:`, откатывается на имя папки.
- `parsePsOutput`: построчный JSON, массив, разный регистр полей, битая строка, пустой вывод.
- `ImageCatalog.build`: дедуп по digest, метки источников, `isCurrent`, сортировка по дате, работа без реестра.
- `TaskManager.startSequence`: успешная цепочка идёт до конца, ненулевой код прерывает остаток, вывод шагов в одном логе, статус `failed`.
- Клиент реестра: URL, заголовок `PRIVATE-TOKEN`, разбор digest и даты.
- `ComposeStore`: переход статусов, `disabled` без docker, `counters()`, снятие пометки `pinned` после `pull`.

Дымовой прогон UI на заглушке blessed: секция compose с фильтром; буквы фильтруют и **не** запускают действий; `Enter` открывает меню; пункт «Логи» создаёт задачу; «Образы и откат» открывает каталог; пункты-записи без подтверждения не делают ничего; после подтверждения уходит ожидаемая цепочка команд.
